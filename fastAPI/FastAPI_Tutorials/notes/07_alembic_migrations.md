# FastAPI — Alembic (DB Migrations)

<!-- Stack: FastAPI 0.115 | SQLAlchemy 2.0 | Alembic 1.x | Python 3.12 -->

---

## Why Alembic (and not `create_all`)

**In my own words:**
`Base.metadata.create_all()` is fine for starting fresh — it creates tables that don't exist. But it can't modify existing tables (add columns, change types, drop columns). Alembic tracks every schema change as a versioned script, so the DB can be upgraded or rolled back.

**Rule of thumb:**
- Dev / greenfield project → `create_all` is fine.
- Any real DB with existing data → use Alembic.

---

## Initial Setup (run once)

```bash
# creates alembic.ini and an alembic/ directory
alembic init alembic
```

**Then edit `alembic/env.py` to point at your models:**
```python
# Generated by GitHub Copilot
# in alembic/env.py
from database import Base          # your DeclarativeBase
import models                      # import models so Alembic can detect them

target_metadata = Base.metadata   # tells Alembic which tables to track
```

**And edit `alembic.ini`:**
```ini
sqlalchemy.url = postgresql://user:pass@localhost:5432/mydb
```

## Core Commands

```bash
# Create a new migration script (--autogenerate detects changes from your models)
alembic revision --autogenerate -m "add phone column to users"

# Apply all pending migrations to the DB (upgrades to latest)
alembic upgrade head

# Rollback the last migration
alembic downgrade -1

# Rollback to a specific revision ID
alembic downgrade <revision_id>

# Show current revision the DB is at
alembic current

# Show full migration history
alembic history
```

## What a Migration File Looks Like

```python
# Generated by GitHub Copilot
# alembic/versions/abc123_add_phone_to_users.py

def upgrade() -> None:
    op.add_column("users", sa.Column("phone", sa.String(), nullable=True))

def downgrade() -> None:
    op.drop_column("users", "phone")
```

**In my own words:**
Every migration has two functions: `upgrade()` (apply change) and `downgrade()` (undo it). Alembic tracks which revision the DB is currently at in a `alembic_version` table.

## `--autogenerate` Limitations

**Gotchas:**
- Autogenerate detects: new tables, dropped tables, new columns, dropped columns, type changes.
- Autogenerate does NOT detect: renaming a column, Python-side `default` values, data migrations.
- Always review the generated migration file before running `upgrade` — autogenerate isn't 100% reliable.
- Changing an Enum value in PostgreSQL requires a custom migration (Alembic can't autogenerate that).

---

## Common Workflow

```
1. Modify your SQLAlchemy model (add/remove a column)
2. alembic revision --autogenerate -m "describe the change"
3. Review the generated file in alembic/versions/
4. alembic upgrade head
```

**Context matters:**
- In the Job Application Tracker, `alembic.ini` is at the project root.
- Run alembic commands from the project root (where `alembic.ini` is), not from inside `app/`.
