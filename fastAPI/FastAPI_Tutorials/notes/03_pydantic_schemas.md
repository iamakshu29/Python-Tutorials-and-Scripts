# FastAPI — Pydantic Schemas (Request & Response Models)

<!-- Stack: FastAPI 0.115 | Pydantic v2 | Python 3.12 -->

---

## Why Pydantic Schemas Exist (separate from SQLAlchemy models)

**In my own words:**
SQLAlchemy models are the DB schema — they define what's in the database.
Pydantic schemas are the HTTP contract — they define what the API accepts and returns.
They are separate on purpose. You never want to expose your raw DB model to the client (it may contain sensitive fields like `hashed_password`).

**Mental model:**

```
Client sent Data → [Pydantic schema validates] → Route logic → [SQLAlchemy model] → Stores in DB
Data stored in DB → [SQLAlchemy model] → Route logic → [Pydantic response schema] → Received by Client
```

## Request Body Schema

**What it does (in my own words):**
Validates and parses the JSON body the client sends. If validation fails, FastAPI automatically returns `422 Unprocessable Entity` — you don't write that logic yourself.

**Modern Pydantic v2 syntax (use this):**
```python
from pydantic import BaseModel, Field, EmailStr, HttpUrl
from enum import Enum

# Restricting to fixed values using enum
class RoleTitle(str, Enum):
    DEVOPS = "Devops"
    TESTER = "Tester"
    DEVELOPER = "Developer"

# Example contains different types of data type used commonly
class ExampleSchema(BaseModel):
    email: EmailStr = Field(examples=["abc@mail.com"])
    original_url: HttpUrl
    role_title: RoleTitle = Field(default=RoleTitle.DEVELOPER)
    urlCode: str | None = Field(min_length=7, max_length=7, default=None)
    title: str = Field(min_length=4, description="Title of the task")
    priority: int = Field(gt=0, le=5, description="Priority 1–5")
    complete: bool = Field(default=False)

# For more data type example check ResponseSchema below
```

**Gotchas:**
- A request schema should only declare the fields the client is expected to send — nothing more. Fields the server fills in (like `id` from the DB or `owner_id` from the JWT) are intentionally left out.
- `id` and `owner` are NOT in the create schema. `id` is auto-assigned by the DB; `owner` comes from the JWT token.
- `EmailStr` requires `pip install pydantic[email]`.
- `Field(gt=0)` = greater than 0. `ge=1` = greater than or equal to 1. They're equivalent for integers.

## Response Schema (DB → Client)

**What it does (in my own words):**
Controls exactly what fields the client gets back. `from_attributes=True` lets Pydantic read from SQLAlchemy model instances directly (instead of only from dicts).

**Modern Pydantic v2 syntax (use this):**
```python
# Generated by GitHub Copilot
from pydantic import BaseModel, ConfigDict
from datetime import datetime, date

from uuid import UUID

class ExampleResponseSchema(BaseModel):
    model_config = ConfigDict(from_attributes=True)  # allows Pydantic to read data from ORM

    id: UUID
    title: str
    created_at: datetime
    applied_date: date
    priority: int
    complete: bool
    status: dict[str, int]
    top_companies: list[str]
    # owner NOT exposed — client doesn't need to see internal foreign keys
```

## `response_model` — Single Object vs List

| Route returns              | `response_model`                 |
| ----------------------------| ----------------------------------|
| `.first()` / single object | `Schema`                         |
| `.all()` / multiple rows   | `list[Schema]`                   |
| aggregate dict             | custom schema matching that dict |

**Gotchas:**
- Wrong type → FastAPI validation error at runtime (e.g. `list[Schema]` on a `.first()` call)
- Fields not in the schema are silently dropped — this is how `hashed_password` is hidden
- `from_attributes=True` required on response schemas so Pydantic can read ORM object attributes

## Context matters:
- `from_attributes=True` is only needed on response schemas where Pydantic needs to read data from ORM
- Not required on request schemas (request schemas just parse dicts from JSON).
- Declare `response_model` in the route decorator to enforce the output shape, e.g.: `@app.get("/user", response_model=TodoResponse)`
- `ConfigDict` accepts other useful parameters too — e.g. `strip_whitespace`, `extra`, `frozen` — you can configure them alongside `from_attributes`.

**Do you need `extra="ignore"` on response schemas?**
No. `response_model` already handles this

**Gotchas:**
- Without `from_attributes=True`, you get `PydanticUserError` when trying to serialize an ORM object.
- `response_model` strips any extra fields not declared in the schema — good for security.

## Partial Update Schema (PATCH)

**What it does (in my own words):**
For PATCH endpoints, all fields are optional. The route only updates the fields the client sent.

**Snippet:**
```python
# Generated by GitHub Copilot
from pydantic import BaseModel, Field

class TodoUpdate(BaseModel):
    title: str | None = Field(default=None, min_length=4)
    description: str | None = Field(default=None, min_length=7)
    priority: str | None = Field(default=None, gt=0, le=5)
    complete: str | None = None
```

**Context matters:**
- Use `model_dump(exclude_unset=True)` in the route to only get fields the client actually sent — ignores fields the client left out.
- `exclude_unset=True` vs `exclude_none=True`: prefer `exclude_unset` for PATCH because a client may intentionally send `null` to clear a field.
